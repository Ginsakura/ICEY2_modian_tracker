## 背景

项目由一条采集链路（`modian_tracker.py`，每 60 秒抓取摩点页面并写入 `data.csv`）和一个分析窗口（`charts.py`，matplotlib 原生控件，5 个视图）组成，纯标准库 + requests/bs4 + matplotlib/numpy，没有数据库也没有 pandas。

当前写入实现（`modian_tracker.py:108-146`）每次采样都：读取整个 `data.csv` → 解析 3 万行 → 追加一行 → `_write_csv` 用 `open(..., "w")` 把全部行重写回磁盘。`data.csv` 现在 2.89MB / 30,801 行，编码 UTF-8 + BOM、行尾 CRLF、时间升序、每分钟一行。写入成本 O(n) 随文件线性增长；更严重的是 `_write_csv` 先截断后写入，重写中途崩溃会直接损坏全部历史数据。

读取端 `BaseChart.load`（`charts.py:277-304`）每次读全文件、按时间戳解析、失败行跳过；`AnalyzeChart` 每 60 秒按 mtime 轮询重载（`charts.py:1000+`）。分析窗口左侧控件列宽 `CTRL_COL_R = 0.16`，视图单选目前 5 项、字号 9，矩形 `(0.015, 0.63, 0.145, 0.255)`；聚合粒度面板在 `(0.015, 0.475, 0.145, 0.105)`，档位显隐在 `(0.015, 0.03, 0.145, 0.355)`。

约束：不引入新依赖；`data.csv` 是唯一数据源且被 git 跟踪（`sync_data.py` 每天 12:00/22:00 自动 commit + push）；采集进程与分析窗口可能同时读写同一文件；众筹 2026-11-15 23:59 截止。

## 目标 / 非目标

**目标：**

- 把常规采样的写入成本从 O(n) 降到 O(1)：单次采样只读表头、只追加一行，历史行零改写。
- 消除「重写中途崩溃毁全表」的窗口：全量重写改为临时文件 + 原子替换。
- 让追加文件保持既有字节约定（单 BOM、CRLF、数值格式），读取端无需改动。
- 新增四个分析视图，覆盖净流拆解、边际结构、日内节律、终局与阶段四类此前不可见的信息。
- 九个视图共用同一份内存数据、同一时间窗口与档位显隐状态。

**非目标：**

- 不改变默认采样间隔（仍 60 秒）；本次只解除瓶颈，加密采样另行评估。
- 不迁移到数据库/列式存储，不拆分按日文件。
- 不做增量加载优化（`load()` 仍是全量重载）。
- 不做订单级明细采集（因此「未支付释放 / 主动取消 / 换档」无法区分）。
- 不自动识别阶段切分点（阶段为人工维护常量）。
- 不改 `--plot` 行为与 CSV 列结构。

## 关键决策

### D1 追加路径用「预渲染整行 + 二进制追加」

用 `io.StringIO()` 配 `csv.writer` 把一行渲染成字符串（默认 `lineterminator="\r\n"`，与现有文件一致），再 `open(CSV_FILE, "ab")` 一次性写入 `line.encode("utf-8")` 字节。

备选方案：直接 `open(CSV_FILE, "a", encoding="utf-8-sig")`。实测在 Linux 下它确实不会在文件末尾重复写 BOM（`TextIOWrapper` 会按流起始位置判断），但该行为依赖 CPython 的 start-of-stream 判定，跨平台/跨版本不够确定，且文本模式的换行翻译还要再靠 `newline=""` 兜一层。二进制追加把编码、BOM、行尾三件事都变成显式可控，代价只是手写 3 字节 BOM（仅首次创建文件时）。

### D2 每次采样校验「表头 + BOM + 行尾」，校验失败才走重写

读表头只读首行（约 400 字节），同时读文件首 3 字节判断 BOM、末 2 字节判断 CRLF。三者任一不符（页面新增档位、文件被外部工具改写成 LF/无 BOM、上次崩溃残留半行）就切到重写路径。不做进程内表头缓存：检测新档位必须看磁盘真实表头，而 400 字节的读成本可以忽略。

### D3 半行修复放在每次追加前，而不是只在启动时

采集进程是长期常驻的，只在启动时修复覆盖不到运行期崩溃。每次追加前 seek 到末尾、读最后 1 字节：若不是 `\n`，从末尾分块向前找最后一个 `\n` 并 `truncate`。成本是 1 次 seek + 1 字节读，异常时才走反向扫描。

### D4 全量重写走临时文件 + `os.replace`

`_write_csv(rows, money_idx)` 改为接受目标路径，重写路径写 `data.csv.tmp`（同目录、同卷），`flush()` + `os.replace()` 原子覆盖。Windows 上同卷 `os.replace` 是原子的；临时文件残留由异常分支清理。这条同时兜住「表头演进」与「编码/行尾不符」两种回退。

### D5 新视图的计算放在 `BaseChart`，绘制放在 `AnalyzeChart`

沿用现有分层：`BaseChart` 有 `parsed`/`header`/`cell`/`aggregate`/`rate_series`，新助手（`daily_totals`、`flow_buckets`、`void_rates`、`marginal_share`、`cumulative_share`、`rhythm_matrix`、`finale_forecast`）都只读内存数据，不碰 IO；`AnalyzeChart` 只负责布局与绘图。所有助手接受 `(lo, hi)` 时间范围（由 `state["window"]` 换成时间戳），这样时间窗口对所有新视图语义一致。

两个口径决策：

- **日增量用跨日末值差**：`日增 = 当日最后一个累计值 − 上一日最后一个累计值`。日内断采不会把日增量算小；缺整日则跳过，图上留空，不用 0 填充。
- **毛增/回吐按原始相邻采样求和**：先在 1 分钟原始步长上取正/负增量，再按聚合桶求和。桶首尾差会把桶内的「先退后买」抵消掉，正好抹掉要研究的回吐。

### D6 视图选择器扩到 9 项：抬高面板、缩小字号

`_ax_view` 由 `(0.015, 0.63, 0.145, 0.255)` 改为 `(0.015, 0.60, 0.145, 0.285)`，标签字号由 9 改为 8。每行约 0.0317 图高（≈ 20.5pt），8pt 字 + 内边距可容纳；与聚合粒度面板顶部（0.58）留 0.02 间距。控件适用性规则扩展为：聚合粒度适用「增速、客单价、净流、边际」；档位显隐适用「趋势、占比、净流、边际」；快照仍只属于占比。

### D7 日内节律用「按日归一 + 缺采掩码」

热力图单元格 = 该小时金额增量 / 当日金额增量之和。不按日归一会被整体衰减趋势吞掉——直接对全期求和会得出「峰值 11 点」这种被趋势污染的结果，按日归一后才是真实节律。用 `numpy.ma.masked_invalid` 承载缺采单元，`cmap.set_bad("#dddddd")` 呈现「无数据」，避免把断采当作 0 参与均值。

### D8 终局外推用双模型包络，不给单点预测

取最近 7 个完整自然日的日增金额，分别做等差外推（每日增量固定为 7 日均值）与对数线性拟合（`ln y = a + b·t`，即指数衰减），外推到 `DEADLINE = 2026-11-15 23:59`。两条轨迹之间填充为区间包络，不做置信区间的统计包装（样本只有 7 个点，置信区间会给出虚假的精确感）。关口 ETA 分别按包络的下限、上限换算成日期区间。数据末行晚于截止时刻时停止外推，只画实际曲线。

等差外推不用对 7 个点做 OLS：这 7 天的日增量本身在单调下滑，OLS 斜率会在截止前把日增量外推到负数，累计曲线随之下折（实测 35.39M，低于当前累计 38.7M），作为「终局」会误导。取均值是保守的常数速率假设，与「对数线性」一起给出快慢两种情景。

### D9 阶段切分为模块常量

`PHASES` 写成 `charts.py` 的模块级常量（P1 起势 10-05~10-08、P2 回落 10-08~10-15、P3 二次脉冲 10-15~10-18、P4 断崖 10-18~10-23、P5 长尾 10-23~截止），来源是探索阶段对日金额的分析。不做自动变点检测：可解释、可复核优先，代价是新增事件需要人工补一条。常量旁注明「与 docs 中的阶段叙事同步维护」。

## 风险 / 权衡

- **读写并发**：写端一次 `write()` 约 150~200 字节，读端仍可能恰好读到半行。缓解：半行修复放在每次写前；`load()` 按时间戳解析失败会跳过残余行；`cell()` 对越界列返回 NaN。概率低、后果可控。
- **外部工具改写文件**：用 Excel 打开再保存会把 CRLF 改掉或去掉 BOM。D2 的编码/行尾校验会触发一次原子重写，把文件拉回约定格式；但重写依赖 `csv.reader` 能解析该文件，若被改得无法解析则拒绝重写并报错，不覆盖原文件。
- **高密度采样的读端成本**：`load()` 每次全量解析，30 万行时重载约秒级；本次不动。若后续把间隔降到 10 秒，需要单独做增量加载（待确认 1）。
- **阶段常量会过期**：新事件发生后图上的阶段带会显得不准；由维护者手工更新，属于已知取舍。
- **外推模型在冲刺末段可能同时失效**（解锁新档位、平台推荐、跨圈传播）。因此只给包络与模型标签，不给「预计达成 X」这类结论式标注。
- **git 体积**：60 秒采样约 210KB/天；加密 6 倍会线性放大。本次不引入归档策略，只在 design 记录。

## 迁移计划

- 无数据迁移。现有 `data.csv` 表头、BOM、CRLF 都符合新写入路径的期望，首次运行直接走追加。
- 上线顺序：先落采集端（P1），在真实进程上观察至少一个采样周期，确认行数 +1、文件前缀校验和不变；再落视图（P2），可离线用现有 `data.csv` 验证。
- 回滚：`git revert` 两个文件即可；`data.csv` 无需回滚（追加行本身就是合法 CSV）。
- 兼容性：列名、列序、行序、数值格式全部不变；`charts.BaseChart.load` 不改；`--plot` 不改；`sync_data.py` 只做 add/commit/push，不受影响。

## 待确认问题（2026-10-28 结论：均暂不采纳）

1. **默认采样间隔**：保持 60 秒，不降到 10 秒。依据是现状数据——60 秒连续跑 23 天，31,686 个应采点里落库 30,801 行（97.2%），唯一的大缺口是 10-21 22:46 → 10-22 11:46 的 13 小时（形态更像设备休眠/断网，不是持续的 403 拒绝）；且处于长尾期（日增约 12 万），1 分钟分辨率已足够。10 秒会让单 IP 请求升到 6 次/分钟，风险虽低于 1 秒级，但收益有限，还会让剩余赛程多出约 15 万行、读端每分钟全量重载变慢。若日后确需加密，建议 30 秒 + 抖动，并要求采集端对空响应/403 退避、读端先做增量加载。
2. **阶段分界可配置**：暂不需要，继续写死在 `charts.py` 的 `CAMPAIGN_PHASES`；改动成本低，等真有第二期数据再说。
3. **订单级采集**：暂不需要。它能区分「未支付释放 / 主动取消 / 换档」，但需要登录态与更高的请求频率，收益不抵风险。
4. **Lv1 默认隐藏**：暂不需要。Lv1 仅 100 份且已售罄，在边际结构里本就不占视觉空间，保留可见更诚实。
